PR proposal 4: Support physical BGA ball names consistently through port resolution
Repositories: https://github.com/tscircuit/core and https://github.com/tscircuit/props
Status: DESIGN PROPOSAL + DIRECT RESOLVER REPRODUCTION; larger API follow-up.

Problem / resulting behavior
The props schema already accepts an alphanumeric pinLabels key such as A1.
However, parsePinNumberFromLabelsOrThrow("DQ0", { A1: "DQ0" }) rejects the key
because downstream code expects pin<number>. The numeric-key workaround
{ pin1: ["A1", "DQ0"] } works. The API therefore accepts a shape that later
fails during pin resolution.
Users should be able to identify a BGA pad by its actual ball name and keep that
identity across footprints, selectors, connectivity and export.

Evidence / relevant code
props/lib/components/chip.ts: pinLabelsProp uses schematicPinLabel for keys.
props/lib/common/schematicPinLabel.ts accepts letters, numbers and underscores.
core/lib/utils/schematic/parsePinNumberFromLabelsOrThrow.ts requires a numeric
key when resolving an alias. getPinNumberFromPinLabelsKey.ts only accepts
numeric and pin-prefixed numeric identifiers.
The direct resolver failure and successful workaround are captured in
bga-pin-reproduction.log. This is not a request to loosen the schema alone.

Proposed implementation
- Introduce a resolved physical-pin identity at the component boundary: retain
  the physical name (A1) separately from any internal numeric ordinal needed
  by schematic layout. Reuse existing canonical identity types where possible.
- Resolve footprint portHints and connections against the physical name and
  explicit aliases; do not derive identity from object insertion order.
- Keep numeric-key behavior stable. If ordinals are needed, derive them from a
  stable package mapping and preserve that mapping through serialization.
- Preserve ball names in emitted ports, diagnostics, readable netlists and PCB
  pad identifiers. Verify the KiCad/export path rather than assuming it follows.
- Reject ambiguous signal aliases with readable pin names. Repeated power labels
  such as GND must not accidentally collapse physically distinct balls.

Acceptance tests
- A1/A2/B1 physical pads connect to the correct ports and traces.
- Equivalent pin maps with different object/footprint ordering preserve identity.
- Existing numeric pins and numeric-key ball aliases stay compatible.
- Multiple GND balls remain distinct pads while joining an explicitly named net.
- Source JSON, schematic, PCB selectors and exported pad identities agree.
- Unknown balls and ambiguous aliases report actionable errors.

Review boundary
This is broader than the small props fix and should follow it separately.
A partial change that makes only one parser accept A1 could introduce unstable
pin numbering or incorrect connectivity elsewhere. Require end-to-end tests.
